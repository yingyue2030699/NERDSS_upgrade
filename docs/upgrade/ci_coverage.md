# CI and Coverage Workflow

The `upgrade-validation` GitHub Actions workflow runs on pull requests and on
pushes to `main` or `codex/**` branches.

## Validation Job

The validation job installs the Linux build dependencies and runs:

```sh
python3 -B tools/run_upgrade_validation.py \
  --output-dir validation-results \
  --fail-fast
```

This covers the serial smoke test, CMake unit-test configure/build/CTest, and
the default regression suite. The workflow uploads `validation-results` as an
artifact even when a step fails.

## Coverage Job

The coverage job uses a separate Debug build with GCC coverage flags:

```sh
cmake -S . -B build-coverage \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_COMPILER=g++ \
  -DCMAKE_CXX_FLAGS="--coverage" \
  -DCMAKE_EXE_LINKER_FLAGS="--coverage"
cmake --build build-coverage --target nerdss_unit_tests --parallel 2
ctest --test-dir build-coverage --output-on-failure
python3 -B tools/collect_gcov_coverage.py \
  --root . \
  --build-dir build-coverage \
  --output coverage-results/coverage-summary.json \
  --text-output coverage-results/coverage-summary.txt
```

`tools/collect_gcov_coverage.py` collects line coverage for project files under
`src/` and `include/` from `.gcda` files generated by `nerdss_unit_tests`. The
job uploads the JSON and text summaries as `unit-coverage-results`.

Coverage flags are passed through `CMAKE_CXX_FLAGS` because the current root
`CMakeLists.txt` sets `CMAKE_CXX_FLAGS_DEBUG` internally.

This is intentionally a reporting job, not a threshold gate. A minimum coverage
threshold can be added through `--fail-under` after the refactor reaches a
stable coverage baseline.
